Writing real integration tests for Phase 3 (the first tests in this project that *write* data) surfaced that Phase 2's tests had been silently running against the same database used for local dev/demo (`ias_disbursements`) — safe by luck for Phase 2's read-only login tests, but Phase 3's create/list tests would have polluted the demo dataset with test rows on every run. Manual curl verification (checking actual server logs, not just reading the code) surfaced a second, more subtle bug: structured log lines for every route under a sub-router (`/api/suppliers`, `/api/disbursement-requests/...`) showed the wrong `path` — either a bare `"/"`, a bare `":id"` pattern with no prefix, or in some cases the mount prefix entirely missing, depending on whether the request succeeded or errored. Root cause: `req.baseUrl`/`req.route` are only valid while a matched sub-router's own handler stack is actively executing — Express resets them as it unwinds back out of that router once `next()`/`next(err)` is called, which for a thrown validation/auth error happens *before* the app-level `errorHandler` (mounted outside the sub-router) ever runs and calls `res.json()`. Verified with a dedicated regression test (`test/requestLogger.test.ts`) that specifically reproduces the error-thrown-inside-a-nested-router scenario and asserts the logged path is still the full, correct pattern.

Rejected it because `docs/TDD.md` §15's own example log line explicitly shows a route pattern with a `:id` placeholder (`"path": "/api/disbursement-requests/:id/approve"`), not a concrete URL — the pattern form is what lets log aggregation group by endpoint shape instead of fragmenting per unique id, which is the whole point of that design choice, so a simpler-but-different behavior wasn't a faithful implementation of the TDD.

### 2026-09-16 — Phase 4: Backend domain (approve/reject with conditional update)

- **Tool:** Claude Code (Claude Sonnet 5), CLI agent with file read/write and shell execution access.
- **Objective:** Implement Phase 4 exactly as scoped in `docs/TDD.md` §20 row 4 and detailed in §6 (state machine) and §8 (concurrent decision strategy): `POST /api/disbursement-requests/:id/approve` and `/reject`, both `SUPERVISOR`-only, using the single-transaction conditional `UPDATE ... WHERE status = 'PENDING'` + `INSERT INTO decisions` pattern so a request can transition out of `PENDING` exactly once, consistently, under concurrency.
- **Accepted output:** The transaction shape from §8 — conditional `UPDATE` first, `INSERT INTO decisions` only if a row came back, both inside `db.transaction()` — was implemented and accepted as designed; it matched the TDD's own SQL sketch almost line-for-line. The decision to distinguish `404` (request truly doesn't exist) from `409` (request exists but wasn't `PENDING`) via a follow-up `SELECT` *after* the failed conditional `UPDATE` — rather than checking existence before attempting the update — was also accepted as designed: it correctly keeps the read used for the 404/409 split out of the concurrency-critical path (the write itself, via row-level locking, is what resolves the actual race; the follow-up read only shapes the error response).
- **Corrected output:** `docs/TDD.md` §8 describes the losing decide call's response as carrying "the request's current (already-decided) status and existing decision info (who decided it, when)," but the error contract built in Phase 2 (`{error:{code,message,correlationId}}`) had no field for that. Implementing the 409 response literally as designed required extending `AppError`/`ConflictError` with an optional `details` payload and having `errorHandler.ts` include it only when present (verified this doesn't change the shape of any *other* error response — the existing `errorHandler.test.ts` `ConflictError` case, which never passes `details`, still asserts the exact 3-key body and still passes). This wasn't caught until actually trying to write the 409 response body and realizing the existing error classes had nowhere to put the extra context — a case of the design doc specifying a response shape richer than the infrastructure built to serve it.
- **Rejected output:** Considered doing the existence check (`SELECT` by id) *before* attempting the conditional `UPDATE`, to return a cleaner 404-vs-409 split without a second query in the failure path. Rejected it because that reintroduces exactly the check-then-act race the whole design exists to avoid: a request could pass the "exists and is PENDING" pre-check and then lose the actual race to another concurrent decide call, leaving the pre-check's information stale by the time the real write happens. Keeping the conditional `UPDATE` as the *only* check, with the disambiguating `SELECT` strictly after it, was the design already specified in §8 — this alternative was discarded, not adopted.
- **Verification performed:** `tsc --noEmit` clean for `src/` and `test/`; `vitest run` passes 55/55 across 11 files, including the concurrency-critical test explicitly named in `docs/TDD.md` §18 Priority 2: `Promise.all([approveCall, rejectCall])` against the same `PENDING` request asserts exactly one `200` and one `409`, that the `409` body's `details.status` matches the actual winner, that a direct `testDb` query finds exactly one row in `decisions` (not zero, not two) matching that winner, and that a follow-up `GET` detail call reflects the same final status — checking the persisted end state, not just the two HTTP responses in isolation. Also verified: approve/reject success shape, missing/blank `reason` on reject → `400`, `ANALYST` attempting to decide → `403`, unauthenticated → `401`, nonexistent id → `404`, malformed id → `400`. Manual curl walkthrough against the dev DB reproduced the exact scenario named in the TDD's own Phase 4 verification bar ("decide twice → second is 409"), including inspecting the full `details` payload on the second call. The manually-created curl demo row (and its associated `decisions` row, deleted first to satisfy the FK) was removed from the dev database afterward.
