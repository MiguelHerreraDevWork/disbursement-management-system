### 2026-09-16 — Phase 1: Project scaffold (monorepo, backend/frontend skeletons, Docker Compose PostgreSQL, Drizzle schema/migration/seed)

- **Tool:** Claude Code (Claude Sonnet 5), CLI agent with file read/write and shell execution access.
- **Objective:** Establish the Phase 1 project foundation exactly as specified in `docs/TDD.md` §4 (Project Structure) and §5 (Domain Model): monorepo layout (`apps/api`, `apps/web`, `docs/`), backend scaffold (TypeScript, Express, Drizzle ORM, Zod env validation, Vitest, Supertest), frontend scaffold (Vite, React 18+, TypeScript, React Router, TanStack Query, Vitest, React Testing Library, MSW), a Docker Compose PostgreSQL 16 service, the initial Drizzle schema/migration for `users`/`suppliers`/`disbursement_requests`/`decisions`, and an idempotent seed script — without implementing business logic, auth, or UI screens (explicitly out of scope for this phase).
- **Accepted output:** The full Drizzle schema (`apps/api/src/db/schema.ts`) generated from the TDD's domain model table-by-table — including the `(supplier_id, external_reference)` composite unique constraint, the `CHECK` constraints on `amount > 0`, `status`, `role`, `decision`, and the conditional "reason required on reject" check — was accepted as-is after comparing the generated migration SQL (`0000_special_morg.sql`) column-by-column against TDD §5 and confirming every constraint/index listed there was present.
- **Corrected output:**
  1. The first pass wired `dotenv/config` (default side-effect import) in both `drizzle.config.ts` and `src/lib/env.ts`, which only loads a `.env` from the current working directory. Since the single shared `.env` lives at the repo root (used by both `docker-compose` and the backend tooling) but these scripts run with `apps/api` as CWD, `drizzle-kit generate` failed with "DATABASE_URL is required." Corrected by explicitly resolving the repo-root `.env` path in both files instead of relying on CWD-relative default loading.
  2. That fix initially used `import.meta.dirname` (Node 22 native) to compute the path, which worked when running via `tsx` but broke drizzle-kit's own config loader (`esbuild-kit`) with "The 'paths[0]' argument must be of type string. Received undefined" — that loader doesn't populate `import.meta.dirname`. Corrected to the more portable `fileURLToPath(import.meta.url)` pattern, which works in both execution contexts.
  3. `npm create vite@latest apps/web -- --template react-ts` was cancelled non-interactively because `apps/web` already contained empty placeholder subdirectories created ahead of time. Corrected by removing the empty dirs and re-running with `create-vite --overwrite --no-interactive`.
- **Rejected output:** `npm audit` flagged 4 moderate-severity advisories in `apps/api` from `esbuild` (a transitive dev-only dependency of `drizzle-kit`'s config loader). `npm audit fix --force` was evaluated but rejected because it would downgrade `drizzle-kit` to `0.18.1`, a breaking change, to fix an advisory that only affects the local dev server accepting arbitrary requests (not a runtime/production risk, and not exploitable outside a developer's own machine). Left as-is and noted here instead of silently forcing a downgrade.
- **Verification performed:** `tsc --noEmit` (backend) and `tsc -b` (frontend) both pass with zero errors; `vitest run` passes in both `apps/api` (Supertest smoke test against the scaffolded Express app) and `apps/web` (MSW-backed fetch-client test + React Testing Library render test); `vite build` succeeds; `docker compose up -d db` brings up `postgres:16-alpine` and reaches `healthy` status; `drizzle-kit generate` + the migration runner applied the schema against the running container; the seed script was run twice in a row to confirm `ON CONFLICT DO NOTHING` idempotency (no duplicate rows); table existence and row contents (2 users — one `ANALYST`, one `SUPERVISOR` — and 3 suppliers) were confirmed directly via `psql \dt` and `SELECT` queries against the container, not just inferred from script output; the dev server was started and `GET /` was curled to confirm the env-loading fix actually resolves at runtime, not only at typecheck time.
- **Sensitive-information safeguard:** No real credentials, production data, or secrets were shared with the tool at any point. `.env` (git-ignored, never committed) and `.env.example` (committed) contain only placeholder local/demo values generated for this exercise (e.g. `JWT_SECRET=demo-local-jwt-signing-secret-change-me`, `POSTGRES_PASSWORD=demo-local-password-change-me`); the seeded demo user password (`Demo-Pass-1234!`) is a throwaway local value, not reused from any real system, and is only valid against the local, disposable Docker Postgres instance.

### 2026-09-16 — Phase 2: Backend core (auth, error handling, logging, health)

- **Tool:** Claude Code (Claude Sonnet 5), CLI agent with file read/write and shell execution access.
- **Objective:** Implement the Phase 2 backend core exactly as scoped in `docs/TDD.md` §20 row 2 and detailed in §9–§11/§15: `POST /api/auth/login` (bcrypt password check, JWT issuance per §10), `requireAuth`/`requireRole` middleware (§10 authorization flow), a central error-handling middleware implementing the `{error:{code,message,correlationId}}` contract (§9, §11), `pino`-based structured request logging with a request-id/correlation-id middleware (§15), and `/healthz`/`/readyz` (§15) — without touching the disbursement-requests business endpoints, frontend, `/metrics`, or Kubernetes (out of scope for this phase).
- **Accepted output:** The JWT claim shape (`{ sub, username, role }`), the `AppError`/`ValidationError`/`UnauthorizedError`/`ForbiddenError`/`NotFoundError`/`ConflictError` hierarchy mapped 1:1 onto the TDD's documented HTTP-status/code pairs, and the `/readyz` design (a real `SELECT 1` through the Drizzle client, 503 on failure, no restart implied) were all accepted as first designed and matched the TDD without rework.
- **Corrected output:** Manual curl verification (not just reading the code) surfaced a real bug: sending a request with syntactically invalid JSON returned `500 INTERNAL_ERROR` with **no** `X-Request-Id` header and no `correlationId` in the body at all — the opposite of what §9's error contract and §15's "every log line carries a correlation id" both require. Root cause was two compounding issues: (1) `express.json()` was registered *before* the `requestId` middleware in `app.ts`, so a request whose body failed to parse never reached `requestId` and had no `req.id` by the time the error handler ran; (2) the error handler only recognized `ZodError` and the custom `AppError` hierarchy as "known" errors, so body-parser's plain `SyntaxError` (thrown with `status: 400`) fell through to the generic 500 branch instead of being treated as the 400 client-input error it actually is. Fixed by reordering `app.ts` so `requestId`/`requestLogger` run before `express.json()`, and by adding an explicit check in `errorHandler.ts` that maps a body-parser `SyntaxError` (`status === 400`) to `400 VALIDATION_ERROR`. Added a regression test (`rejects syntactically invalid JSON as a 400, not a 500...` in `test/auth.test.ts`) and re-verified with curl that the response now returns `400`, a populated `correlationId`, and a matching `X-Request-Id` header.
- **Rejected output:** Considered using `pino-http` for automatic HTTP request/response logging instead of hand-written `requestId`/`requestLogger` middleware. Rejected it because `pino-http`'s default log shape (raw `req`/`res` objects, `responseTime`) doesn't match the exact field list `docs/TDD.md` §15 specifies (`reqId, method, path, userId, role, operation, result, statusCode, durationMs`, with `result` distinguishing `success`/`conflict`/`error`) without non-trivial custom serializers — writing the two small, explicit middleware functions was more direct, easier to unit-test, and easier to audit for the "never log auth material" requirement than configuring around a library's defaults.
- **Verification performed:** `tsc --noEmit` clean for both `src/` and `test/` (added a `tsconfig.test.json` so test files are typechecked too, since Vitest's esbuild transform doesn't type-check); `vitest run` passes 20/20 across 5 files (login success for both roles incl. real JWT decode/verify, wrong password, nonexistent user, missing-field validation, malformed-JSON body, health/ready endpoints, `requireAuth`/`requireRole` unit tests for every branch, error-handler mapping for a known `AppError`, an unexpected error, and the 404 fallback); manual curl matrix against the running dev server: `/healthz` → 200 (and still 200 with the DB stopped), `/readyz` → 200 `{"status":"ok","db":"ok"}` with DB up, 503 `{"status":"unavailable","db":"unreachable"}` immediately after `docker compose stop db`, and 200 again after `docker compose start db` once the container reported healthy; `POST /api/auth/login` curled for both demo users, returning a real JWT whose `exp - iat` was confirmed to equal exactly 8h; captured dev-server log output was grepped for `password|bearer|authorization` (case-insensitive) with zero matches; `git log -p` (only one commit exists so far, made directly by the developer, not by this tool) was grepped for `password|secret` and manually reviewed — every match was a placeholder value, a column/variable name, or documentation prose, never a real secret.
- **Sensitive-information safeguard:** No real credentials, production data, or secrets were shared with the tool. The same local/demo-only values from Phase 1 (`JWT_SECRET`, `POSTGRES_PASSWORD`, the seeded demo user password) were reused for verification; no new secrets were introduced, and none were logged (verified by grep, see above).
